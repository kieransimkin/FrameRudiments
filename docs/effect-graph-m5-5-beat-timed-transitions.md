# M5.5 — Beat-authoritative, reversible and repeatable transition timing

**Status:** implementation candidate (v23); requires full project CI before acceptance.

**Baseline:** FrameRudiments v22 commit `d73bc2e4731034b32c35b6231d412ee59877bf8b`.

## Purpose

Transition timing is an optional *pure function of the existing project beat clock*. No new beat tracker, wall clock, oscillator, mutable smoothing accumulator, or frame history is introduced. This works for static BPM, confirmed beat grids, and sample-pinned variable-BPM timelines. Beat 1 offset, input provenance, native 64-pip phase, and source repeat behaviour remain owned by `Project`.

All `transition` nodes, including stages generated by `transition_chain`, can define a `timing` object. A transition without it keeps its old `progress` behaviour byte-for-byte. The graph's resolved control values are copied per frame; authored JSON is never changed by rendering or by seeking.

A transition-chain stage accepts the *same* `timing` object; after expansion its binding path is the stable ID `chain-id::stage::stage-id`. The chain continues to compile into normal graph nodes and shares the same alpha, GPU fallback and snapshot contracts.

## Timing properties

| Field | Default | Accepted values | Meaning |
| --- | --- | --- | --- |
| `clock` | `continuous` | `continuous`, `source` | Use `ctx.beat` across audio repeats, or `ctx.source_beat` that restarts at each source repeat |
| `start_beat` | `0` | -100000 … 100000 | Absolute beat at which the envelope begins |
| `duration_beats` | `4` | 1/64 … 4096 | Active transition length in beats |
| `phase_beats` | `0` | -4096 … 4096 | Offset evaluated beat phase, including negative phase shifts |
| `repeat` | `once` | `once`, `loop`, `pingpong` | Hold final state, repeat a forward cycle, or alternate forward/reverse cycles |
| `period_beats` | `duration_beats` | duration … 8192 | Period between cycle starts; extra interval holds the completed state |
| `preset` | `linear` | `linear`, `smoothstep`, `ease_in`, `ease_out`, `ease_in_out`, `triangle`, `pulse`, `bounce` | Normalized progress response |
| `reverse` | `false` | boolean | Invert final progress (after curve/keyframe evaluation) |
| `steps` | `0` | `0` or integer 2 … 64 | Quantize normalized beat phase into discrete positions before the curve |
| `keys` | absent | 2 … 32 `{at,value,ease?}` points | Custom non-monotonic progress envelope, replacing `preset` |

`keys` must begin at `at=0`, end at `at=1`, and strictly increase in `at`. Values may reverse arbitrarily within [0,1]. Segment easing can be `linear`, `smoothstep`, or `hold`. Providing both `keys` and `preset` is rejected. All numeric parameters require finite numbers; `steps` must be integral. `period_beats` is valid only when `repeat` is `loop` or `pingpong` and must be at least `duration_beats`.

### Repeat semantics

* **Once:** before start, progress 0; after duration, progress 1 (subject to the chosen curve, `keys`, and `reverse`).
* **Loop:** at the period boundary, begin the next forward cycle. If period exceeds duration, hold the previous cycle's terminal value until the next cycle.
* **Ping-pong:** reverse normalized phase on odd cycles. At period boundaries there is no jump in the phase (provided each curve itself has matching endpoint values).
* **Continuous vs source clock:** `Project.continuous_beat(frame)` increments across repeated audio, whereas `Project.clock.beat_at(Project.source_time(frame))` restarts with the source loop. Both use the project's actual tempo map, never a nominal display BPM.
* **Non-monotonic curves:** `pulse`, `triangle`, and custom keys may intentionally return to the outgoing source at the end. Do not force `progress=1` at the endpoint in these modes.

### Control precedence

1. `effect_graph_controls` generates numeric or categorical overrides from native DanceRudiment motions.
2. `timing.*` overrides modify only the *current frame's* temporary timing definition; combinations are validated after all changes.
3. If **`progress` was explicitly bound for the current frame**, it wins over the generated timer progress.
4. Otherwise, the timing engine calculates progress from the requested frame's beat. Any subsequent effect executes with normal graph rules.
5. If `context=None` (manual pure image graph render), existing static `progress` is used; no implicit clock is constructed.

All meaningful numeric and discrete timing parameters are addressable as `timing.<name>` through existing `effect_graph_controls`. `timing.preset` is not available for an authored keyframe curve. `keys` themselves remain an authored structural definition, not a continuously modulated array.

## Testable acceptance gates

- Invalid envelopes, numeric bounds, cycles, categorical choices and unsuitable node types fail at graph preparation.
- Beat-timed endpoints, loops, ping-pong seams, gaps, reverse, pulse and non-monotonic keyframes are covered by isolated regression tests.
- Direct random-access evaluation is byte-identical regardless of the order of previously rendered frames.
- `continuous` and `source` policies have different, documented results over a repeated audio project.
- Variable-BPM grid uses actual beat anchors; no constant-BPM approximation.
- Original native DanceRudiment progress bindings override timer progress without mutating graph configuration.
- Chained transition stages have stable IDs and share all timing functionality.
- Visual evidence generator produces a deterministic 5×6 contact sheet and JSON manifest with per-frame SHA-256 values.
- `ruff check .`, full `pytest` matrix, native-project tests, and existing GPU parity workflow must pass after merge. Timing itself runs on CPU as metadata/control evaluation; existing GPU node execution is unchanged.

## Dependencies / design boundaries

Runtime dependencies remain Python 3.11+, Pillow 10+, the existing native DanceRudiments clock, and optional NumPy for image blending. No new packages are required. Beat-synced timing is independent of the selected GPU backend, including future GPU-resident DAG scheduling. Audio files, beat grids, and recording sources remain checksum-pinned under the established project validation model.

**Deferred:** authoring UI timeline controls, GPU-resident multi-node execution, editor waveform previews, MIDI/OSC live timing, and temporal feedback. These are separately gated future milestones.
